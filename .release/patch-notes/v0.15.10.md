## Highlights

Where 0.15.0 shipped the read API and the event plumbing, this release fills in the live data behind it. Watch sessions are now per-device, so the same account on two TVs shows as two sessions. Every client reports its actual play/pause/buffer state, so the `playback.*` events that were reserved in 0.15.0 now fire, and webhooks and SSE carry the full picture: who is watching, on which device, what program, how far behind live, and whether it is playing or paused. The admin Sessions page gains brand logos and a live status badge per viewer, and Samsung TVs are recognized as Samsung instead of a generic browser.

## New Features

- **Per-device watch sessions.** A watch session is now keyed per (user, device) instead of per user, so the same account watching different things on two TVs shows as two live sessions, each with its own `deviceId`. Clients that don't send a device id collapse to a single `"legacy"` session, unchanged. This also fixes a latent bug where two devices on one account clobbered each other's transcode-reap tracking.
- **Live playback state, and the `playback.*` events now fire.** `playback.started`, `playback.stopped`, `playback.paused`, and `playback.resumed` were reserved and shown as "coming soon" in 0.15.0; they now fire, driven by the actual player state a client reports in its heartbeat. `channel.tuned` returns too, firing when a device changes channel within a session.
- **Enriched event payloads.** Every session and playback event (webhook and SSE) now carries the same detail as the "Now Watching" view: the device id, the channel (number/name/callsign), the current program (title/show/season/episode/year), the live `playbackState`, how far behind live (`delaySeconds`), and `progress` (position and duration in the program). A consumer can react straight off the payload without a follow-up call.
- **All four clients report playback state.** tv-web (LG/Samsung/browser), tv-tauri (desktop), tv-native (iOS/Android/Apple TV), and tv-roku each send their `deviceId` and `playbackState` (playing/paused/buffering/idle) in the heartbeat and fire an immediate beat on a play/pause transition, so `playback.*` events land in about a second rather than on the next 10s tick. The mpv and Roku clients keep one session across channel changes (emitting `channel.tuned`); the browser/TV-web client surfaces a channel change as a stop then start. Legacy or third-party clients that don't report state still produce `session.*`, just without the `playback.*` detail.
- **Reaped sessions get a proper end.** The watch-session reaper now emits `session.ended` (plus `playback.stopped`) with the full enriched payload before clearing a stale session, so a crashed, closed, or disconnected session (or one a server restart left behind) gets the same closure a clean exit would, instead of leaving a consumer stuck. A quick server restart while watching keeps the session alive, since the client keeps heartbeating.
- **Device info and live playback state on the admin Sessions page.** Each active session tile shows the device's brand logo (LG, Samsung, Roku, Apple, Android, Windows, or a browser) and a friendly label (for example "LG OLED77C2AUA", "Roku Streaming Stick 4K", "Apple TV") instead of a bare model string or "Unknown", plus a Playing / Paused / Buffering / Idle badge from the reported playback state. Device resolution is hybrid: the session's own `deviceId` first, falling back to the play-log's device for legacy sessions.
- **Samsung Tizen is its own platform.** The tv-web client now reports `platform: "tizen"` on a Samsung TV instead of a generic `browser`, parses the Tizen OS version from the user agent, and fills in the real panel model via Samsung's `webapis.productinfo` (for example "QN55Q7F"). So a Samsung shows as a Samsung TV, with its model, wherever device info surfaces.
- **Device info on the public session endpoints.** `GET /api/public/v1/sessions` now carries `deviceId`, `playbackState`, and a richer `device` (`id`, `platform`, `model`, `osVersion`, `hdr`) when the device is registered, and `GET /now-playing` gains a compact `device` (`model`, `platform`). Additive and best-effort, so existing consumers and older clients are unaffected (fields are simply `null` when unknown).

## Fixes

- **No more phantom `playback.resumed` on the desktop and mobile clients.** tv-tauri and tv-native derived playback state buffering-first, but mpv reports `core-idle` (the buffering signal) as true while paused, so a steady-state heartbeat a few seconds after pausing looked like a resume to the server. The clients now check paused before buffering, so a paused player stays paused.

## Docs

- **Webhooks and Live events (SSE) guides updated.** The `playback.*` events are documented as live (no longer "coming soon"), with `channel.tuned` and how a channel change surfaces per client. The payload section shows the full enriched `data`, and a new "Per-device sessions" section explains the per-(user, device) keying and the `"legacy"` fallback. The SSE guide points at the same payload reference, and the Home Assistant now-playing example surfaces the new `device` attribute. The interactive API reference and the spec-driven docs mock pick up the new fields automatically from the regenerated OpenAPI spec.

## Migration

- **`watch_session_per_device`** adds `deviceId` (default `"legacy"`) and `playbackState` to the watch-session table plus a `@@unique([userId, deviceId])`. Applied automatically on the server's pre-deploy `prisma migrate deploy`.
